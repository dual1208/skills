# Project glossary format

Use the project's existing layout. In a small project, one CONTEXT.md is enough.

Each entry names the term and explains it in one or two sentences. Add an example when it makes the meaning clearer. Use the user's established term rather than replacing it with a more elaborate synonym.

A simple entry:

**Camouflage**: Making the public endpoint behave like a normal website for requests without the correct secret.

Use an "Avoid" line only for alternatives that caused actual confusion. General programming vocabulary does not need a project-specific glossary entry.

Keep the glossary separate from deployment status and design proposals. Definitions say what words mean; they do not claim that the described feature is running.

If CONTEXT-MAP.md already directs readers to several glossaries, follow that structure. Do not create multiple contexts just to organize a small set of terms.
